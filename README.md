# Визуализатор графа зависимостей пакетов Cargo

Практическая работа № 2, вариант 9. Этап 4 — дополнительные операции.

## 1. Общее описание

Инструмент командной строки (CLI) для анализа и визуализации графа
зависимостей пакетов менеджера Cargo (язык Rust). Готовые менеджеры
пакетов и сторонние библиотеки для получения зависимостей
не используются, только стандартная библиотека Python.

Все параметры задаются в конфигурационном файле формата XML.
Программа читает конфигурацию, получает зависимости пакетов из
реестра Cargo по URL-адресу (или из файла тестового репозитория),
строит граф зависимостей с учётом транзитивности алгоритмом BFS без
рекурсии и выводит его, а затем выводит порядок загрузки зависимостей.
Учитываются максимальная глубина анализа, фильтр по подстроке и
циклические зависимости.

Код находится в каталоге `src`, тесты — в `tests`.

## 2. Функции и настройки

### Запуск

```text
python src/main.py [ПУТЬ_К_КОНФИГУРАЦИИ]
```

Если путь не указан, читается `config.xml` из текущего каталога.

### Параметры конфигурации

Корневой тег — `<config>`. Внутри задаются параметры:

- `package` — имя анализируемого пакета. Имя пакета Cargo (латинская
  буква, затем буквы, цифры, `_`, `-`); в тестовом режиме — большие
  латинские буквы.
- `repository` — URL-адрес репозитория (начинается с `http://` или
  `https://`) или, в тестовом режиме, путь к файлу тестового
  репозитория (файл должен существовать).
- `test_mode` — режим работы с тестовым репозиторием: `true` / `false`
  (также `yes` / `no`, `1` / `0`).
- `output_file` — имя файла с изображением графа, оканчивается на `.svg`.
- `ascii_tree` — режим вывода зависимостей в виде ASCII-дерева:
  `true` / `false`.
- `max_depth` — максимальная глубина анализа зависимостей, целое
  число от 1.
- `filter` — подстрока для фильтрации пакетов. Необязательный
  параметр; латинские буквы, цифры, `_`, `-`.

Пример (`config.xml`):

```xml
<config>
    <package>serde_json</package>
    <repository>https://index.crates.io</repository>
    <test_mode>false</test_mode>
    <output_file>serde_json.svg</output_file>
    <ascii_tree>true</ascii_tree>
    <max_depth>2</max_depth>
    <filter></filter>
</config>
```

### Обработка ошибок

Программа проверяет все параметры сразу и выводит полный список
найденных ошибок, после чего завершается с кодом 1. Обрабатываются:

- отсутствующий файл конфигурации, повреждённый XML, неверный
  корневой тег;
- отсутствующий или пустой обязательный параметр;
- неизвестный параметр и повторно заданный параметр;
- недопустимое имя пакета (отдельные правила для тестового режима);
- URL без `http://` / `https://`, отсутствующий файл тестового
  репозитория;
- значение `test_mode` и `ascii_tree`, не являющееся логическим;
- имя файла изображения не с расширением `.svg`;
- глубина, не являющаяся целым числом или меньше 1;
- недопустимые символы в подстроке фильтра.

Примеры ошибочных конфигураций лежат в каталоге `configs/errors`.

### Получение зависимостей (формат Cargo)

Данные берутся из индекса реестра пакетов Cargo в разреженном
(sparse) формате — так же, как это делает сам Cargo. По умолчанию это
`https://index.crates.io`. Для каждого пакета в индексе есть текстовый
файл, путь к которому строится по имени:

- 1 или 2 символа: `1/a`, `2/ab`;
- 3 символа: `3/s/syn`;
- 4 и более: первые две буквы, следующие две, имя —
  `se/rd/serde_json`.

Каждая строка файла — JSON-описание одной версии пакета с полем `deps`.
Файл скачивается модулем `urllib` стандартной библиотеки, менеджеры
пакетов и сторонние библиотеки не используются.

Правила выбора данных:

- берётся новейшая версия по правилам semver (`1.10.0` новее `1.9.0`);
- отозванные (yanked) версии пропускаются, pre-release версии
  используются, только если других нет;
- прямыми зависимостями считаются обычные (`normal`) обязательные
  зависимости; dev- и build-зависимости, а также необязательные
  (optional) пропускаются;
- для переименованных зависимостей выводится настоящее имя пакета.

Ошибки репозитория: пакет не найден (HTTP 404, 410, 451), другие
ошибки HTTP, недоступный адрес, некорректные данные индекса.

Для транзитивных зависимостей берётся новейшая версия каждого пакета
(требование к версии, например `^1.0`, не сопоставляется), а
зависимости для конкретных платформ (`target`) учитываются все сразу.

### Построение графа (BFS)

Граф строится в модуле `src/graph.py` обходом в ширину с очередью
`collections.deque`, без рекурсии:

1. В очередь кладётся анализируемый пакет (глубина 0).
2. Из очереди берётся пакет; если его глубина меньше `max_depth`,
   запрашиваются его прямые зависимости.
3. Зависимости, имя которых содержит подстроку `filter`, не
   учитываются: они не попадают в граф и их зависимости не
   запрашиваются. Сам анализируемый пакет фильтром не отбрасывается.
4. Пакеты, которые ещё не встречались, получают глубину на 1 больше и
   добавляются в очередь.

Глубина `max_depth = N` означает N уровней зависимостей: пакеты на
уровне N попадают в граф, но их зависимости уже не запрашиваются
(в выводе — «не анализировался: достигнута максимальная глубина»).

Циклические зависимости: каждый пакет добавляется в очередь только
один раз, поэтому цикл не приводит к бесконечному обходу. После
построения циклы ищутся итеративным обходом в глубину (стек вместо
рекурсии) и выводятся отдельным списком, например `A -> B -> C -> A`.

### Режим тестового репозитория

При `test_mode = true` в `repository` указывается путь к текстовому
файлу описания графа. Пакеты называются большими латинскими буквами:

```text
# комментарий
A: B C
B: D
C: D
D:
```

Слева от двоеточия — пакет, справа — его прямые зависимости через
пробел. Пакет, упомянутый только как зависимость, считается пакетом
без зависимостей. Ошибки: неверный формат строки (с номером строки),
повторное описание пакета, отсутствие анализируемого пакета в файле.

Примеры графов в каталоге `examples`:

- `simple.txt` — граф без циклов с общей зависимостью;
- `cycle.txt` — цикл `A -> B -> C -> A` и петля `D -> D`;
- `chain.txt` — длинная цепочка для проверки глубины;
- `names.txt` — многобуквенные имена для проверки фильтра;
- `broken.txt` — файл с ошибкой формата.

Готовые конфигурации для них — в `configs/test`.

### Порядок загрузки зависимостей

После графа программа выводит порядок загрузки: каждый пакет стоит
после всех своих зависимостей, анализируемый пакет — последним. Это
обратный топологический порядок графа. Он вычисляется функцией
`load_order` в `src/graph.py` итеративным обходом в глубину
(постпорядок, стек вместо рекурсии); зависимости обходятся в том
порядке, в котором перечислены у пакета.

Если в графе есть цикл, правильного порядка не существует: ребро,
замыкающее цикл, пропускается, а программа сообщает, какие рёбра не
учтены. Ограничение глубины и фильтр действуют так же, как при
построении графа.

### Сравнение с Cargo

Скрипт `scripts/cargo_compare.py` превращает файл тестового
репозитория в настоящий workspace Cargo: каждый пакет становится
крейтом, зависимости подключаются через `path`. Затем запускается
`cargo build -j 1 --offline` (сборка в один поток, без сети), и
порядок строк `Compiling …` сравнивается с порядком визуализатора.
Для запуска нужен установленный Rust (`cargo`).

```text
python scripts/cargo_compare.py examples/simple.txt A
```

Результаты на тестовых репозиториях (Cargo 1.97, сборка в один поток):

| Граф, пакет | Визуализатор | Cargo | Итог |
|---|---|---|---|
| `chain`, A | G F E D C B A | G F E D C B A | совпадает |
| `names`, APP | UTIL LOG CORE TLS NETUTIL NET APP | то же | совпадает |
| `simple`, C | G E F C | G E F C | совпадает |
| `simple`, A | D G E B F C A | G E D F C B A | отличается |
| `cycle`, A | E D C B A (+ предупреждение) | ошибка `cyclic package dependency` | отличается |

Причины расхождений:

- **Топологический порядок не единственный.** В `simple` пакеты D и G
  друг от друга не зависят, и любой из них можно загрузить первым.
  Оба порядка корректны: каждый пакет идёт после своих зависимостей.
  Визуализатор обходит зависимости в порядке их перечисления (сначала
  ветка B, потом C), а планировщик Cargo в первую очередь собирает
  пакеты с самой длинной цепочкой зависимых (G → E → B → A), чтобы
  при параллельной сборке быстрее освободить остальные задачи.
- **Параллельная сборка.** По умолчанию Cargo собирает независимые
  пакеты одновременно, и порядок строк `Compiling` может меняться от
  запуска к запуску; поэтому сравнение делается с `-j 1`.
- **Циклы.** Cargo запрещает циклические зависимости между пакетами и
  завершается ошибкой, а визуализатор строит порядок без замыкающего
  ребра и предупреждает об этом.

Для реальных пакетов crates.io расхождения появляются ещё и потому,
что визуализатор упрощает модель Cargo:

- берётся новейшая версия каждого пакета, а Cargo подбирает версии по
  требованиям (`^1.0` и т. п.) и объединяет их для всего проекта;
- необязательные зависимости (optional) пропускаются, а Cargo
  подключает те из них, которые включены функциями (features) по
  умолчанию;
- build-зависимости пропускаются, а Cargo собирает их раньше пакета
  (для сценариев `build.rs`);
- зависимости для всех платформ учитываются сразу, а Cargo берёт
  только зависимости текущей платформы.

Проверить на реальном пакете можно так (нужны Rust и интернет):

```text
cargo new demo && cd demo
cargo add serde_json
cargo build -j 1 -v
```

## 3. Сборка и тесты

Сборка не нужна, требуется Python 3.8 или новее.

Запуск:

```sh
sh run.sh config.xml
```

```bat
run.bat config.xml
```

Тесты:

```sh
python -m unittest discover -s tests -v
```

Тесты не обращаются к интернету: для проверки HTTP-запросов они
поднимают локальный сервер с файлами в формате индекса crates.io.

Демонстрация обработки ошибок для всех параметров:

```sh
sh scripts/demo_errors.sh
```

```bat
scripts\demo_errors.bat
```

Сравнение порядка загрузки с настоящим Cargo (нужен Rust):

```sh
sh scripts/demo_cargo_compare.sh
```

```bat
scripts\demo_cargo_compare.bat
```

Графы и порядок загрузки на всех тестовых репозиториях
(`configs/test/*.xml`):

```sh
sh scripts/demo_test_repo.sh
```

```bat
scripts\demo_test_repo.bat
```

Графы реальных пакетов crates.io (`config.xml` и
`configs/real_*.xml`, нужен доступ в интернет):

```sh
sh scripts/demo_real.sh
```

```bat
scripts\demo_real.bat
```

Простой тестовый граф:

```text
$ python src/main.py configs/test/simple.xml
Граф зависимостей пакета A
Максимальная глубина: 10
A -> B, C
B -> D, E
C -> E, F
D -> нет зависимостей
E -> G
F -> нет зависимостей
G -> нет зависимостей
Пакетов в графе: 7
Циклические зависимости: не найдены

Порядок загрузки зависимостей пакета A:
  1. D
  2. G
  3. E
  4. B
  5. F
  6. C
  7. A
```

Циклические зависимости:

```text
$ python src/main.py configs/test/cycle.xml
Граф зависимостей пакета A
Максимальная глубина: 10
A -> B
B -> C
C -> A, D
D -> D, E
E -> нет зависимостей
Пакетов в графе: 5
Циклические зависимости:
  A -> B -> C -> A
  D -> D

Порядок загрузки зависимостей пакета A:
  1. E
  2. D
  3. C
  4. B
  5. A
Порядок неполный: из-за циклов пропущены рёбра C -> A, D -> D
```

Ограничение глубины (`max_depth = 2` на цепочке A → B → … → G):

```text
$ python src/main.py configs/test/depth_2.xml
Граф зависимостей пакета A
Максимальная глубина: 2
A -> B
B -> C
C -> не анализировался: достигнута максимальная глубина

Циклические зависимости: не найдены

  1. C
  2. B
  3. A
```

Фильтр `NET`: пакет NET исключён, а NETUTIL и TLS, достижимые только
через него, в граф не попадают:

$ python src/main.py configs/test/filter_net.xml

  1. UTIL
  2. LOG
  3. CORE
  4. APP
```

crates.io):

```

Пакета нет в репозитории:

```text
$ python src/main.py configs/real_missing.xml

  - пакет не найден в репозитории: https://index.crates.io/no/-s/no-such-crate-kola-su
```

Ошибки во всех параметрах сразу:

```text
$ python src/main.py configs/errors/all_errors.xml
Ошибка конфигурации:

```
